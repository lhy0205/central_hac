# 통신 구조 및 서버 주소 운영 가이드

**현재 구성: 서버가 두 대다.** 백엔드+DB는 한 호스트(예: 가비아 서버)에, AI 서버 2개(하자 탐지,
AR 인식 — 저장소 `MCM_ai`)는 별도의 "외부 AI 서버"에 각각 떠 있다. 예전에는 한 서버에
`docker-compose.yml` 하나로 전부 올렸지만(그때 문서가 이 파일의 이전 버전), AI 서버가 별도
저장소·별도 호스트로 분리되면서 통신 경로가 인터넷을 한 번 더 타게 됐다. 설치·실행 절차는
[`DEPLOY.md`](./DEPLOY.md)를 참고한다.

## 1. 한눈에 보기

```
  ┌──────────┐                  ┌── 가비아 서버 ──────────────┐
  │          │──:8080──────────▶│ backend (Spring)            │
  │          │                  │      │                      │
  │ 모바일 앱 │                  │      │ :5432 (내부망)        │
  │          │                  │      ▼                      │
  │          │                  │  db (Postgres)               │
  │          │                  └──────┼──────────────────────┘
  │          │                         │ :8000 + X-API-Key (인터넷)
  │          │                         ▼
  │          │                  ┌── 외부 AI 서버 ──────────────┐
  │          │                  │  defect-detection (하자 탐지) │
  │          │──:8001──────────▶│  ar-identification (AR 인식)  │
  └──────────┘                  └──────────────────────────────┘
```

핵심은 세 가지다.

- **앱은 서버 두 곳(가비아 백엔드, 외부 AI 서버의 AR 인식)을 각각 직접 호출한다.** 이 둘은 서로
  독립적이다. AR 인식은 백엔드를 거치지 않는다.
- **하자 탐지는 앱이 직접 부르지 않는다.** 백엔드만 접근하지만, 이제 같은 서버 내부망이 아니라
  **인터넷 너머**로 호출한다 — 그래서 API 키 인증이 붙는다(3절).
- **DB는 백엔드만 접근한다** — 여전히 같은 호스트 안이라 인터넷에 노출되지 않는다.

## 2. 포트와 방화벽

| 서비스 | 호스트 | 포트 | 호출하는 쪽 | 인바운드 개방 |
|---|---|---|---|---|
| `backend` | 가비아 서버 | 8080 | 모바일 앱 | **필요** |
| `db` | 가비아 서버 | 5432 | `backend` (같은 호스트) | 불필요 (내부 전용) |
| `defect-detection` | 외부 AI 서버 | 8000 | `backend` (인터넷 너머) | **필요** — 대신 API 키로 막는다 |
| `ar-identification` | 외부 AI 서버 | 8001 | 모바일 앱 (직접) | **필요** |

예전 구성과 달리 `defect-detection`도 이제 인바운드를 열어야 한다 — 백엔드가 더 이상 같은
호스트에 없기 때문이다. 그 대신 **인증 없이 열어두면 안 된다** — 3절의 API 키를 반드시 설정할 것.
`db`(5432)는 여전히 외부에 열지 않는다.

## 3. 외부 AI 서버 호출: 주소 + API 키

컨테이너 내부 네트워크(서비스 이름)로 통신하던 것과 달리, 백엔드와 하자 탐지 서버는 이제
서로 다른 호스트에 있어 **일반적인 인터넷 HTTP 호출**로 통신한다. 아무나 호출 못 하게 API 키를
같이 보낸다.

| 설정 | 값 | 위치 |
|---|---|---|
| 백엔드 → 하자 탐지 주소 | 외부 AI 서버의 공인 주소 (예: `http://<AI서버주소>:8000`) | `MCM_backend/.env`의 `DEFECT_API_URL` |
| 백엔드 → 하자 탐지 인증키 | AI 서버의 `API_KEY`와 동일한 값 | `MCM_backend/.env`의 `DEFECT_API_KEY` |
| AI 서버가 요구하는 키 | 위와 동일한 값 | 외부 AI 서버의 `API_KEY` 환경변수 |
| 백엔드 → DB | `jdbc:postgresql://db:5432/mcm_passport` (같은 호스트 내부망, 변경 없음) | `docker-compose.yml`의 `DB_URL` |

`DEFECT_API_KEY`를 비워두면 백엔드는 인증 헤더 없이 호출한다 — AI 서버 쪽 `API_KEY`도 비어
있을 때만(즉 둘 다 미설정) 정상 동작하고, 그 경우 **누구나 그 서버로 무료 추론을 돌릴 수 있다.**
가비아처럼 외부 호스트로 나가는 구성에서는 양쪽에 반드시 같은 값을 넣는다. 자세한 서버 쪽
설정은 [`../MCM_ai/defect-detection/HANDOFF.md`](../MCM_ai/defect-detection/HANDOFF.md#인증-인터넷에-노출할-경우-필수) 참고.

`ar-identification`은 원래부터 앱이 직접 호출하는 구조라 이번 분리로 통신 경로 자체는
바뀌지 않았다 — 다만 물리적으로 백엔드와 다른 호스트에 있다는 점만 명확히 해 둔다. 현재
이 서버 자체에는 별도 인증이 없다(앱에 박아 넣는 키는 APK에서 추출 가능해 방어 효과가
제한적이기 때문 — 필요해지면 별도로 검토).

> **평문 HTTP로 붙이면 API 키도 평문으로 나간다.** 같은 서버 내부망일 때는 문제가 안 됐지만,
> 지금은 인터넷 구간을 지나므로 중간에서 `X-API-Key` 헤더를 그대로 읽을 수 있다. 데모 수준
> 위험 감수가 가능하면 당장은 그대로 가도 되지만, 여유가 있다면 외부 AI 서버 앞에 리버스
> 프록시(Caddy/nginx)로 TLS를 씌우거나, 방화벽에서 가비아 서버의 고정 IP만 8000에 접근하도록
> 제한하는 걸 권장한다.

**서버 IP/도메인이 바뀌어도 코드는 손댈 필요가 없다** — 값은 전부 `.env`에 있다. 바뀌면
`.env`를 고치고 재시작하면 된다(앱이 바라보는 주소는 예외 — 4절).

## 4. 앱이 바라보는 서버 주소

### 왜 신경 써야 하나

앱의 서버 주소는 `EXPO_PUBLIC_*` 환경변수로 지정하는데, 이 값은 **Metro가 번들링할 때
문자열로 치환해서 APK 안에 그대로 박아 넣는다.** 즉 배포된 앱의 서버 주소는 서버 쪽
`.env`를 고쳐도 바뀌지 않고, 앱을 다시 빌드해야만 바뀐다.

```
MCM_frontend/.env
  EXPO_PUBLIC_API_BASE_URL=http://<가비아 서버 주소>:8080
  EXPO_PUBLIC_AR_API_BASE_URL=http://<외부 AI 서버 주소>:8001
```

두 값은 **서로 다른 서버**를 가리킨다 — 하나로 통일해서 넣지 않도록 주의.

> 앱은 사용자 폰에서 도는 프로그램이라 서버처럼 실행 시점에 환경변수를 읽을 수 없다.
> "환경에 따라 알아서 들어가게" 만드는 건 원리상 불가능하고, 아래 두 가지로 대응한다.

### 원칙: 고정 주소를 박고 그대로 간다

서버 주소가 고정이면 이걸로 충분하다. 최종 주소로 한 번 빌드하면, 설치한 사람은 아무것도
입력하지 않고 바로 쓴다. **데모용 APK는 반드시 최종 서버 주소로 빌드할 것** — 개발 중
쓰던 사설 IP(`172.x`, `192.168.x`)가 박힌 채로 나가면 외부에서는 접속 자체가 안 된다.

```bash
cd MCM_frontend
# .env를 최종 서버 주소로 고친 뒤
npx eas-cli build --profile preview --platform android
```

주소가 자주 바뀔 가능성이 있다면 IP 대신 **도메인**을 박는 게 정석이다. IP가 바뀌어도 DNS
레코드만 고치면 앱은 그대로 동작한다.

### 보험: 앱 안에서 주소 재정의

데모 당일 주소가 틀어졌을 때 재빌드·재설치 없이 그 자리에서 고치기 위한 비상구를 넣어 뒀다.

- **여는 법**: 프로필 탭 → 화면 상단의 "프로필" 제목을 **길게 누르기**
- **동작**: 저장된 재정의 값이 있으면 그걸 쓰고, 없으면 빌드에 박힌 기본값을 쓴다

```
저장된 주소 있음?  ──아니오(새로 설치한 기기)──▶  빌드에 박힌 기본값 사용
                   └─예(우리가 직접 넣음)─────▶  저장된 주소 사용
```

새로 설치한 기기는 저장된 값이 없으므로 **항상 기본값으로 동작한다.** 심사위원은 이 화면의
존재를 알 필요도, 주소를 입력할 일도 없다. 설정 화면에서 입력란을 비우고 저장하면 기본값으로
되돌아간다.

관련 코드: `src/config/serverAddress.ts`(주소 해석), `app/dev/server.tsx`(설정 화면)

## 5. 사진이 오가는 경로

진단 사진은 서버를 두 번 지난다.

1. 앱이 백엔드로 사진 업로드 (`multipart/form-data`)
2. 백엔드가 Cloudinary에 올리고 URL을 받음
3. 백엔드가 **그 URL로 사진을 다시 내려받아** 하자 탐지 서버에 바이트로 전달
4. 하자 탐지 결과를 백엔드가 진단 기록으로 저장

그래서 **하자 탐지 컨테이너는 인터넷에 나갈 필요가 없다.** 외부로 나가는 트래픽은 백엔드의
Cloudinary 호출뿐이다.

AR 인식은 이 경로와 무관하다 — 앱이 사진을 AR 서버로 직접 보내고 결과를 바로 받는다.

## 6. 알아둘 제약

- **평문 HTTP** — 지금은 TLS 없이 붙는 구성이라 안드로이드에서만 동작한다
  (`app.json`의 `usesCleartextTraffic: true`). iOS 기기로 시연할 계획이 있다면 도메인 +
  리버스 프록시(TLS)가 먼저 필요하다. 같은 이유로 백엔드 → 외부 AI 서버 구간도 기본은
  평문이다(3절의 경고 참고).
- **OTA 업데이트 없음** — `expo-updates`가 설치돼 있지 않아, 앱 코드를 고치면 APK를 다시
  배포해야 한다. 4절의 주소 재정의는 이 제약을 서버 주소에 한해서만 우회한다.
- **AR 서버는 독립적이다** — 모델이 이미지에 구워져 있어 런타임 외부 호출이 없다. 백엔드가
  죽어도 AR 인식 자체는 계속 동작한다.

## 7. VLM(AI 종합 진단)을 켤 경우

이 절은 가비아 서버가 아니라 **외부 AI 서버 쪽** 설정이다. `WEAR_DIAGNOSIS_ENGINE=vlm`으로
켜면 하자 탐지 컨테이너가 (그 컨테이너가 떠 있는) 호스트의 Ollama(`:11434`)를 호출하는 홉이
하나 더 생긴다. 이때 **컨테이너 안의 `localhost`는 호스트가 아니라 컨테이너 자기 자신**이라
기본값으로는 절대 닿지 않는다.

```
defect-detection 컨테이너 ──localhost:11434──▶ (컨테이너 자신, 연결 실패)
defect-detection 컨테이너 ──host.docker.internal:11434──▶ 호스트의 Ollama ✅
```

- 이 지정을 가능하게 하는 작업이
  [`docs/superpowers/plans/2026-08-18-vlm-grade-integration.md`](./docs/superpowers/plans/2026-08-18-vlm-grade-integration.md)의
  Task 4다 (`OLLAMA_HOST` 환경변수화).
- **GPU가 없다면 이 홉을 만들지 않는 쪽이 안전하다.** YOLO 하자 탐지는 CPU에서 실측
  0.5~0.7초/장으로 충분하지만, VLM(`qwen2.5vl:7b`)은 CPU에서 이미지 한 장에 수 분이 걸리고
  RAM도 5~6GB를 추가로 쓴다. S/A/B/C/D 등급 자체는 `WEAR_DIAGNOSIS_ENGINE=ml`에서도 그대로
  나오므로, VLM 없이 가도 등급 기능은 잃지 않는다 — 잃는 건 자연어 판정 근거 한 줄이다.

## 8. 서버 주소가 바뀌었을 때 체크리스트

가비아 서버(백엔드)와 외부 AI 서버 중 **어느 쪽 주소가 바뀌었는지**에 따라 고칠 파일이 다르다.

### 가비아 서버(백엔드) 주소가 바뀐 경우
- [ ] 가비아 서버에서 `docker compose up -d`로 backend+db가 떠 있는지 확인
- [ ] 방화벽에 8080 인바운드가 열려 있는지 확인
- [ ] `curl http://<가비아서버>:8080/api/health` 응답 확인
- [ ] `MCM_frontend/.env`의 `EXPO_PUBLIC_API_BASE_URL`을 새 주소로 수정
- [ ] 앱 재빌드 후 배포 (`npx eas-cli build --profile preview --platform android`)
- [ ] 재빌드가 불가능한 상황이면 → 앱에서 프로필 제목 길게 눌러 주소 직접 입력 (4절)

### 외부 AI 서버 주소가 바뀐 경우
- [ ] 외부 AI 서버에서 defect-detection(8000), ar-identification(8001) 컨테이너가 떠 있는지 확인
- [ ] 방화벽에 8000, 8001 인바운드가 열려 있는지 확인
- [ ] `curl http://<AI서버>:8000/health`, `curl http://<AI서버>:8001/health` 응답 확인
- [ ] `MCM_backend/.env`의 `DEFECT_API_URL`을 새 주소로 수정 후 가비아 서버에서 `docker compose up -d backend` 재시작
- [ ] `DEFECT_API_KEY`(백엔드)와 `API_KEY`(AI 서버)가 여전히 같은 값인지 확인
- [ ] `MCM_frontend/.env`의 `EXPO_PUBLIC_AR_API_BASE_URL`을 새 주소로 수정 후 앱 재빌드
