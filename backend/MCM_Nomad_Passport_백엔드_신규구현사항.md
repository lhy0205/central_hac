# 백엔드 신규 구현 필요사항 — 2차 개정 기획서 기준 (최신화)

> 비교 기준: `MCM_Nomad_Passport_구조_요약.md`(기존 백엔드 구조) ↔ `MCM_Nomad_Passport_기획서_2차개정.docx`(현재 최신 기획서, 오태훈 멘토 2차 리뷰 반영본)
> 결론: **여권 승계(소유권 이전) + STORE 도메인이 신규**로 필요하고, ERD·클래스·시퀀스 다이어그램에 이미 반영 완료. 나머지는 범위 확인만 하면 됨.

---

## 1. 신규 구현 확정 — 여권 승계(소유권 이전)

기획서 4장, 그림1(360° 흐름도)·그림2(유스케이스)·7장 데모범위에 공통으로 등장. 그림2(유스케이스)에 정식 유스케이스로 추가 완료, ERD·클래스 다이어그램에 `OwnershipTransfer` 엔티티로 반영 완료.

### 1-0. 확정된 정책 (2026-08-10 팀 결정)

- **purchaseYear = 현재 소유자의 구매연도.** 승계가 완료되는 시점에 새 소유자의 실제 구매연도로 값을 갱신한다. (최초 출고연도가 아님 — 중고 구매자가 모를 수 있는 값을 요구하지 않기 위함)
- **Passport 삭제는 되돌릴 수 없다.** `DELETED → ACTIVE` 복구 전이는 만들지 않는다. 삭제 시 "지금까지의 진단·케어 기록이 모두 사라집니다"라는 경고를 보여준다.
- **동일 시리얼+구매연도로 재등록은 가능하지만 이전 이력과 연결되지 않는다.** 삭제된 개체를 같은 시리얼로 다시 등록하면 **새 Passport row(새 id)**가 생성되고, 완전히 새 제품으로 취급한다. 승계 절차를 건너뛴다고 해서 이전 소유자의 진단·케어 이력을 가져올 수는 없다. (예전 Diagnosis/CareRecord/TimelineEvent는 옛 Passport id에 남아있지만 새 등록에서는 조회되지 않음)
- 이 정책으로 "남의 가방 시리얼만 알면 이력까지 복구·탈취할 수 있다"는 멘토 지적(Passport 상태다이어그램 vs 본문 모순)이 구조적으로 해소됨

### 1-1. 데이터 모델 (신규 엔티티, ERD 반영 완료)

```
OwnershipTransfer
├── id (PK)
├── passportId (FK → Passport)
├── fromAccountId (FK → Account)      # 원 소유자
├── toAccountId (FK → Account)        # 새 소유자
├── transferCode                      # 6자리 영숫자, unique
├── status                            # ISSUED / REDEEMED / EXPIRED
└── transferredAt

Store                                 # 신규, TimelineEvent.storeId가 참조
├── id (PK)
├── name
└── address
```

- `Passport.ownerAccountId`는 승계 완료 시점에 새 소유자로 갱신
- `Passport.purchaseYear`도 승계 완료 시점에 새 소유자의 실제 구매연도로 갱신 (확정 정책, 1-0 참고)
- `Diagnosis`, `CareRecord`, `TimelineEvent`는 모두 `passportId`만 참조하므로 소유자가 바뀌어도 이력 자체는 자동으로 유지됨 (별도 마이그레이션 불필요)
- **미확정**: 새 소유자가 이전 소유자 시절의 진단 원본 사진(`Diagnosis.imageUrls`)까지 볼 수 있는지, 아니면 등급·점수만 보이고 사진은 마스킹되는지 — 정책 결정 필요

### 1-2. API 엔드포인트 (신규 3개)

```
POST   /api/passports/{id}/transfer-code        # 승계 코드 발급 (원 소유자만 가능)
GET    /api/passports/transfer/{code}/preview    # 승계 대상 제품 정보 미리보기 (와이어프레임 "승계하려는 제품이 맞나요?" 모달용)
POST   /api/passports/transfer/redeem            # 승계 코드 입력 → 소유권 이전 실행
```

### 1-3. 에러 케이스 (신규)

| 상황 | 상태코드 / 코드 |
|---|---|
| 코드 형식 불일치 | 400 `INVALID_TRANSFER_CODE_FORMAT` |
| 코드 만료/이미 사용됨 | 400 `TRANSFER_CODE_EXPIRED_OR_USED` |
| 자기 자신에게 승계 시도 | 400 `CANNOT_TRANSFER_TO_SELF` |
| 코드 재입력 불일치 (발급 시) | 400 `TRANSFER_CODE_CONFIRM_MISMATCH` |

### 1-4. 데모 포함 여부 — 여전히 미확정

기획서 그림1·그림2·4장에서는 여권 승계를 서비스가 지향하는 완성된 그림의 핵심 축으로 다루지만, 이는 "이번 해커톤 데모에 실제로 포함된다"는 뜻은 아님을 7장에 명시해 둠. 데모범위 표에는 "실동작(확인 필요)"로 별도 행이 있음.
→ **여권 승계 기능 자체를 이번 해커톤 데모에 넣을지 여부를 팀에서 먼저 확정해야 함.** (6절 참고)

## 2. 신규 구현 확정 — Store 엔티티 (경량)

`TimelineEvent.storeId`가 매장 방문 기록을 가리키는데, 지금까지 Store 자체가 데이터 모델에 없어 FK가 허공을 가리키는 상태였음(오태훈 멘토 2차 리뷰 지적). 최소 스펙으로 신설:

```
Store
├── id (PK)
├── name
└── address
```

- 매장 목록은 초기에는 시드 데이터(하드코딩 또는 마이그레이션 스크립트)로 채워도 충분 — 매장 등록/관리 API는 이번 MVP에 불필요
- `TimelineEvent.type = STORE_VISIT`일 때만 `storeId`가 채워지는 구조로 설계

## 3. 서비스 레이어 명시화 (구현 가이드, 데이터 모델 변경 아님)

클래스·시퀀스 다이어그램을 2차 개정하면서 아래 두 서비스 클래스를 명시적으로 분리했음. 실제 구현 시 이 경계를 따르는 것을 권장:

- **DiagnosisService**: 컨트롤러로부터 진단 요청을 위임받아 Cloudinary 업로드 → 이전 진단 조회 → `WearDiagnosisEngine` 호출 → `Diagnosis` 저장까지 담당
- **LifecycleCurator**: `DiagnosisService`로부터 알림 평가 요청을 받아 `Diagnosis`를 읽고 `Notification`을 생성. 스케줄러(재진단 리마인드)도 이 클래스가 담당

이렇게 나누면 `WearDiagnosisEngine`(AI 교체 지점)과 알림 로직이 서로 독립적으로 테스트·교체 가능해짐.

## 4. 확인만 하면 되는 것 (구조 변경 불필요)

- **AR / Concierge**: 유스케이스 다이어그램 각주에 "이번 백엔드 MVP 범위 밖의 프런트엔드 전용 기능"이라고 명시됨 → 백엔드 작업 없음. **AR은 팀에서 이미 프로토타입 구현(카메라로 촬영하면 해당 물품 정보를 띄우는 수준)까지 확인해 데모 포함으로 확정**. 데모범위 표에는 아직 "목업·영상"으로 분류되어 있음 — 프로토타입이 이미 있다면 "실동작"으로 재분류할지 팀 확인 필요
- **인증서 발급**: "관리 이력이 충분히 쌓인 고객에게 무료로 제공할 계획"으로 표현이 계획형으로 정리됨. 데모범위 표에는 여전히 "로드맵" — 발급 로직은 이번 MVP에 안 만들어도 됨
- **매장 스탬프(오프라인 루프)**: 그림1에 별도 단계로 그려져 있지만, 실질적으로는 `Diagnosis.diagnosisType = STORE` + 신규 `TimelineEvent(type=STORE_VISIT, storeId)`로 커버됨. 추가 엔티티 불필요

## 5. 이전 와이어프레임 검토에서 나왔지만 이번 기획서엔 아직 반영 안 된 것

- `Notification.type`에 "기념(마일스톤)" 타입 없음 (SELF_CARE/STORE_SERVICE/REPURCHASE 3종뿐)
- `Notification`에 "종합 O점" 표시용 점수 필드 없음
- `TimelineEvent`에 기록 유형(순간기록/매장방문/셀프케어/기타) 필드는 이번에 `type`으로 추가됨(2절 참고) — 다만 순간기록/셀프케어/기타까지 세부 enum 값을 다 정의할지는 미확정
- **공식 케어 예약**: 와이어프레임엔 매장선택(지도/거리)+캘린더 시간슬롯+요청항목 체크리스트까지 있는 완전한 예약 시스템인데, 기획서엔 여전히 "행동 연결(공식수선 예약 **버튼**)" 수준으로만 표현됨 — 실제 예약 도메인(매장, 시간슬롯, 예약건)을 새로 만들 것인지 아직도 불명확

## 6. 팀에 확인이 필요한 질문 (2026-08-12 기준)

1. **여권 승계를 이번 해커톤 데모에 포함하나?** — 데이터 모델·API 설계는 끝났으나(1절), 실제 구현 착수 여부는 미결
2. 승계 시 새 소유자가 이전 진단 원본 사진까지 보게 할지, 등급·점수만 보이게 할지 — **미결**
3. 공식 케어 예약을 실제 예약 시스템(매장/시간슬롯)까지 만들지, 버튼 하나로 축소할지 — **미결**
4. Notification "기념" 타입과 종합점수, TimelineEvent 세부 유형(순간기록/셀프케어/기타) — 이번 MVP에 넣을지 다음 스프린트로 미룰지 — **미결**
5. AR을 "실동작"으로 데모범위 표에 재분류할지 — 프런트 담당자(심지윤) 확인 필요 — **미결**
